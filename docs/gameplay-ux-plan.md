# Cow Skate — план улучшений геймплея и UX

Рабочий документ для обсуждения агентами. Не спека «высечено в камне» —
здесь разбор проблем, варианты решений, открытые вопросы и порядок внедрения.
Перед реализацией прочитать актуальный код: `backend/app/static/game/*.js`

`cow-skate-standalone.html` генерируется (`make standalone`) — руками не

## A. Туториал с паузами («гейты»)

### Проблема текущего тренера

`setCoach()` показывает строку на фиксированное время (1.7–3.2 с) во время
игры — читать на бегу не успеваешь. `ПРЫГАЙ!` бессрочный, но остальные шаги
мигнут и исчезли.

### Дизайн: пауза-гейты вместо тикеров

Игру можно остановить целиком: `frame()` пропускает `update()`, когда
`S.paused` — сцена замерзает на текущем кадре (canvas держит последний
кадр, рендер можно не крутить). `S.t` не движется → таймеры тренера,
автопилот (`lastInput`), частицы — всё корректно заморожено. При резюме
`dt` мгновенно не взлетит: `update(min(dt, 1/20))` уже клампит; плюс
во время паузы продолжать обновлять `last = now`, чтобы не ловить
«долгий кадр» на выходе.

Поверх — DOM-карточка `.tutor`: заголовок, 1–2 строки, кнопка «Дальше».
Ввод блокируется: `act()`/`jump()`/`trick()`/`throttle` ранний выход при
`S.paused`; резюм — только кнопка (по фидбеку важно, чтобы читали, а не
промахивали тапом). Кнопка — обычный DOM, вне canvas.

### Очередь гейтов (только первый заезд)

Триггер → пауза → текст → кнопка → продолжение. Хранить флаг
`localStorage 'cow-skate-tutored'` — вернувшимся игрокам не показывать.

Черновая последовательность:

1. **Старт заезда** (первый тап из демо): «Ты — корова на скейте.
   Тап по экрану — прыжок».
2. **Первое препятствие ≤ ~1.5 с** (только на земле, не в полёте):
   «Впереди препятствие. Тап — перепрыгнуть. За него +50». На паузе
   препятствие и маркер «!» видны застывшими — можно спокойно найти глазами.
3. **После первого приземления с прыжка**: «В воздухе можно ещё один тап —
   двойной прыжок. Линейки/барьеры (×2) только так».
4. **Первый трамплин ≤ ~2 с**: «Трамплин! В полёте жми кнопки трюков —
   каждый трюк × очки».
5. **Первая петля** (если делаем B): «Мёртвая петля — нужен разгон!
   Зажми экран заранее и не отпускай».

После гейта 4 ставим `coachStage = 3` и `cow-skate-tutored` — старый
тренер больше не дергается. Тикеры из деплоя 36377ae остаются
запасным каналом (короткие «+50», совет после пустого крэша) либо
упрощаются — решить при реализации.

### Граничные случаи

- Пауза разрешена только на земле и не в крэше (иначе зависание в воздухе
  выглядит багом). Если условие гейта сработало в воздухе — отложить до
  приземления.
- `coachStep`/`autopilot` не вызываются при `S.paused` (автопилот не
  прыгнет «за игрока» во время чтения).
- Мировые координаты не зависят от `S.t` — пауза не ломает `feats`,
  `cracks`, `spawnFeatures` (спавн идёт по `camX`, он заморожен).
- Звук/сеть не затронуты; `cowskate:run-end` в паузе не стреляет.
- Частота: гейты только в первом заезде и только по одному — очередь,
  а не каскад.

## B. Мёртвая петля (loop-the-loop)

### Физика — посчитано под наши константы

Всё в «ростах коровы»: `GRAV = 7.6`, `CRUISE = 4.2`, `MAXSPD = 7.6`,
`MINSPD = 2.3` (index.html, константы игры).

Честная петля: вход снизу со скоростью `v0`, радиус `R`. Энергетика:
`v_top² = v0² − 4·g·R`. Условие удержания на вершине `v_top² ≥ g·R`
→ **`v0 ≥ sqrt(5·g·R)`**.

| R (cowH) | v0 мин (честная грав.) | v0 мин (g×0.6 на петле) |
|---|---|---|
| 0.50 | 4.36 | 3.37 |
| 0.55 | 4.57 | 3.53 |
| 0.70 | 5.16 | 4.00 |
| 0.90 | 5.85 | 4.53 |

Вывод: при честной гравитации петля R≥0.55 недоступна на крейсерской
скорости — нужен разгон (hold, `S.throttle=1` → MAXSPD). Это даже плюс:
петля даёт смысл механике «зажми — разгон», которая сейчас почти
неоткрываема. Вариант «помощи» — ослабить g на дуге (×0.6), тогда
R=0.7 проходится почти на крейсерской. Решить: честная+требует разгона
(интереснее, учит механике) vs мягкая+прощающая (казуальнее).
Промежуточный вариант: честная физика, но небольшая «магнитная» помощь
только в верхней трети дуги.

### Модель движения на петле (вариант: параметрическая дуга, не полная sim)

Полноценная физика контакта не нужна — достаточно параметра `θ`:

- `θ ∈ [0, 2π)`: 0 — вход снизу, π — вершина. Позиция коровы:
  `X = Xc + R·sinθ` (мир), `h = R·(1−cosθ)`; угол спрайта = `θ + π/2`
  (копыта к центру... точнее по касательной — проверить на макете).
- Угловая скорость `ω = v/R`; интегрируем: `ω += (−g·sinθ)/R · dt`
  (тангенциальная гравитация тормозит подъём, разгоняет спуск).
- Вход: захват при `boardX ≥ X0` если `v0` достаточна → режим
  `S.loop = {f, θ, ω}`; обычная `physicsStep` для высоты выключается,
  поза задаётся дугой. Выход при `θ ≥ 2π` → `launch()`-подобный выброс
  или просто продолжение езды.
- Недобор скорости (честный вариант): если `ω` упал ниже порога до θ=π
  → откат назад по дуге (весёлый fail без крэша, попап «НЕ ДОТЯНУЛ —
  НУЖЕН РАЗГОН»); если потеря контакта в верхней части (`v² < g·R·sinθ`)
  → срыв внутрь петли → `crash()`.

Альтернатива — полностью скриптовая петля (canned анимация по дуге за
фиксированное время). Проще, но «нечестно»: нет недобора/срыва и трюк
на дуге встроить труднее. Рекомендация — параметрическая дуга выше:
та же простота, но физика настоящая.

### Трюки на петле

Во время `S.loop` кнопки трюков работают: таймер как в воздухе, поза
добавляет `S.roll/spin` поверх угла дуги. Очки: базово +150 за проход
петли («ПЕТЛЯ!»), трюк на дуге ещё +100 и считается в `mult` при выходе.
Незавершённый трюк на выходе — тот же `bail` что при приземлении.

### Рендер

- Конструкция петли: два рельса + шпалы по дуге + опоры — рисуем
  полилиниями в `drawRamp`-стиле (тот же приём `P(X,h,z)` проекции,
  ближняя/дальняя стенки с `zn/zf`).
- Камера: при входе `S.zoomOut` кратковременно больше (петля ~1.8·cowH
  высотой — должна влезать целиком; механика zoomOut уже есть).
- Спрайт коровы вращаем через `poseMatrix` (roll уже умеет полный
  оборот — `S.roll` для сальто); гравитационные детали (ухо, бирка)
  в идеале привязать к локальной вертикали петли — фаза «мелочи»,
  можно отложить.

### Спавн

- `feats` уже умеет смешанные типы; добавить `type: 'loop'` с весом
  (редко — раз в ~30–60 с) и запретом ближе ~6·cowH к другим фичам
  после выхода с петли (нужна чистая зона приземления).
- Длинный ровный подход перед петлёй: не спавнить препятствия ближе
  ~8·cowH до `X0` — игроку нужно место «зажать разгон».

## C. Больше видов трамплинов

Каждый — параметры спавна (вес, зазор), геометрия в `groundInfo`/дуге,
отрисовка, очки. По убыванию «выгода/сложность»:

1. **Высокий кикер** (`hr 0.45–0.55`): больше воздуха → 2 трюка.
   Минимальная новая логика — та же рампа, другой `hr`. Дёшево.
2. **Стол/tabletop**: рампа вверх — плато — рампа вниз; на плато можно
   прокатиться или спрыгнуть даблом. Геометрия — `groundInfo` с тремя
   участками, рисунок — обобщённый `drawRamp`.
3. **Пропасть (gap)**: две рампы с дырой между; падение в дыру = крэш.
   Новый fail-режим (`groundInfo` отдаёт `h = −deep`, порог срыва),
   рисунок — обрыв асфальта. Учит «зачем разгон»: разогнался — перелетел
   красивее/дальше.
4. **Волны/вупс (whoops)**: 3–4 низких холма подряд — ритмичные
   мини-прыжки/отскоки (`bumpAt` уже умеет удары по колёсам).
5. **Кольцо/монета над рампой** (+100): награда за точный вылет —
   задаёт «куда прыгать». Дёшево: чек позиции в воздухе + спрайт.
6. **Мёртвая петля** — отдельный раздел B.

Порядок спавна: веса в `OBS`-стиле таблице + ограничение «не более одного
спец-фича на N метров». Плотность обычных препятствий не трогаем.

## D. Библиотеки — разбор по чести (обсуждение после теста)

Проект: **один файл без сборки**, canvas 2D, своя поза через
`DOMMatrix`, кастомная перспектива дороги.

### Поправка к первой версии раздела

«Слишком жирно по весу» — слабый аргумент, снимаю: matter-js ≈ 30 КБ
gzip — меньше зашитых в файл спрайтов коровы. Грузится из CDN или
кладём в `static/` — влияние на время загрузки почти нулевое.
Настоящая цена — **архитектурный конфликт**, см. ниже.

### Что на самом деле нужно вишлисту

Вишлист: больше трюков, комбинации, разные препятствия, трамплины,
«происшествия» (ивенты). Разложим по тому, что каждый пункт требует:

| Хотелка | Что это технически | Нужна ли physics-либа |
|---|---|---|
| Новые трюки (indy, shove-it, методы-хваты) | поза-анимация по таймеру, как `stepTrick` + новый спрайт-поворот | нет |
| Комбо-система | уже есть зародыш: `trickQ` + `mult` за связку в одном воздухе; расширить — цепочки между приземлениями, нейминг, окна | нет |
| Грайнд на перилах/проводах | «на рейле» = состояние с параметрическим скольжением по линии — как петля, один DOF | нет |
| Мануал (езда на задних колёсах) | состояние + баланс-метр | нет |
| Новые препятствия | строка в `OBS` + спрайт + вес спавна | нет |
| Новые трамплины/петля/gap | параметрическая дуга/`groundInfo` — см. B/C | нет |
| Ивенты (птица, боковой ветер, скользкая лужа, НЛО) | скрипт на таймере + модификатор состояния | нет |
| Рагдолл при крэше (корова кубарем с конечностями) | rigid body | **да** |
| Летящий мусор, который можно пнуть и он врезается в конусы | rigid body, контакты | **да** |
| Качающиеся/падающие конструкции, качели-балансиры | rigid body | **да** |

Вывод по таблице: 90% расширения игры — это **анимации, спавн-паттерны
и машины состояний**, а не физика. Runner-игры индустрии почти все так
и живут (Subway Surfers и ко. — скриптовая «физика ощущения»).

### Почему matter-js прямо сейчас — плохая покупка

Нынешняя корова — не твёрдое тело: у неё пружины-подвески (`bob/tilt/
sq/ear/tag`), приседания, моушн-призраки. Чтобы physics-движок вёл
корову, надо либо всю её «мультяшную» физику выразить в rigid body
(будет чувствоваться хуже без долгой настройки), либо держать две
физики параллельно и синхронизировать — дорого и багоёмко. Для петли
(одна степень свободы θ) — 30 строк формул против движка.

### Когда библиотека себя окупит

Если/когда захотим фичи из нижних строк таблицы: рагдолл-крэши
(корова реалистично кувыркается с конечностями), пинаемый мусор,
конструкции-домино. Тогда matter-js подключается **точечно для этой
подсистемы** — спрайт коровы остаётся на нашей физике, а обломки/
объекты живут в движке и читаются из него при рендере. Это аддитивно,
не переписывание.

### Куда реально упрёшься раньше (важнее библиотек)

При +10 типах фич файл превратится в ~3000 строк — узкое место будет
**организация кода**, не физика. Полезнее:
- разнести фичи трассы в data-driven описания (таблица видов +
  `spawn/draw/check` хуки на тип) — добавление трамплина = +строка в
  таблице и спрайт, а не правки в пяти местах;
- при желании — ES-модули (`<script type="module">` работает без
  сборки), файл снова станет обозримым.

**Вердикт (обновлённый):** библиотеку физики не подключать сейчас;
не закрываем дверь — при первой фиче «много тел + контакты»
(рагдолл, пинаемый мусор) оцениваем matter-js для неё одной. Рост
игры держать на data-driven фичах и, если файл раздуется, на модулях.

### Зафиксированный скоуп physics-библиотеки (решение от 2026-09-29)

Библиотека — **только точечно, под конкретные фичи**, не для игры
целиком. Текущая корова и трасса всегда остаются на своей
скриптовой физике (пружины, DOMMatrix-позы, перспектива).

Кандидаты под physics-движок (оценивать при постановке фичи в работу):

- рагдолл-крэш: корова кубарем с конечностями вместо scripted bail;
- пинаемые/бьющиеся объекты: мусор, бочки, которые летят и сбивают
  конусы цепочкой;
- разрушаемые конструкции-домино, качели-балансиры, подвесные штуки;
- что-то ещё «много тел + контакты» — критерий: ≥2 тела, которые
  должны толкать друг друга и правдоподобно падать/катиться.

Правила скоупа: движок (ориентир — matter-js, ~30 КБ gzip) живёт
изолированно для фичи, корова на него не мигрирует; объекты движка
рисуются нашим рендером (читаем состояние тел, рисуем спрайтами).
Если фича не в списке — сначала пытаемся параметрически/скриптом,
либу подключаем только когда скрипт объективно не тянет.

## E. Модульность — рефакторинг однофайловой игры

**Статус (2026-09-29): выполнено** — полный вариант (~10 модулей +
`utils.js`), чистый move без изменения логики. Проверено: eslint
(`no-undef`/`no-import-assign`/`no-unused-vars`), `node --check`, pytest,
детерминированный headless-прогон (seeded `Math.random`, ручные кадры,
скриптованный ввод) — пиксели canvas и DOM-состояние идентичны до/после
для `index.html` и standalone.

Отличия от эскиза ниже, продиктованные ES-модулями (импорты read-only):
- `update()` — в `main.js` (цикл кадра), камера пишется через `setCAM()`;
- `W/H/DPR/perfScale` и `X0/X1` живут в `layout.js` (пишет их только
  `layout()`), `perfScale` из цикла — через `setPerfScale()`;
- текстуры/изображения, которые раньше присваивал boot, собирает
  `initAssets()`/`initShadow()` в `sprites.js`;
- `playerMode`, массивы сцены (`feats`, `parts`, `cracks`…) — в `state.js`;
  поза коровы (`poseMatrix`…) и автопилот — в `player.js`, `setT/setCam` —
  в `render.js`, `drawCracks` — в `effects.js`;
- standalone собирается в порядке исполнения ES-модулей; событие
  `cowskate:run-end` в нём теперь тоже есть (без слушателя — no-op).

### Почему он нужен

Главная боль — не длина файла, а **зеркало**: каждую правку приходится
вносить в `index.html` и `cow-skate-standalone.html` руками. Уже было
бы дорого; с фичами A–C станет источником багов-рассинхрона.
Дополнительно: ~90% объёма файла — base64-спрайты, которые мешают
читать код и диффы.

### Подход: ES-модули без сборки

`<script type="module">` работает нативно (Telegram webview — современные
WebKit/Chromium, ок). Бандлер не нужен: файлы отдаёт FastAPI static
по HTTP/2 тем же origin. Правило «секции» уже есть в файле —
резать по существующим `// ---` границам.

```
backend/app/static/
  index.html            # тонкая оболочка: DOM, CSS, <script type="module" src="game/main.js">
  game/
    assets.js           # META + SRC (base64) — уехали из глаз
    state.js            # S, G, CAM, флаги, canvas/ctx, DOM-refs — живые биндинги модулей
    constants.js        # OBS/TRICKS/скорости/гравитация
    layout.js           # layout(), zAt/yAt/xAt/obZ/obPos
    sprites.js          # текстуры: дорога/поле/облака/препятствия/корова-кэши
    player.js           # jump/trick/land/crash/physicsStep, поза (poseMatrix…)
    features.js         # spawnFeatures/groundInfo/checkObstacles + draw*
    effects.js          # частицы, попапы, линии, cracks, камера-тряска
    render.js           # sky/ground/cow/post, render()
    ui.js               # hud, cta/coach/result, input handlers
    main.js             # boot + frame loop
tools/build-standalone.py   # собирает те же модули в один файл
cow-skate-standalone.html   # ГЕНЕРИРУЕМЫЙ артефакт (make standalone)
```

- `state.js` экспортирует общий мутируемый стейт — ES-биндинги живые,
  код из IIFE переезжает почти verbatim, минимальный риск.
- `standalone` больше не правится руками: скрипт (python, без
  зависимостей) подставляет модули инлайном, сохраняя свойство
  «один файл открывается из file://» (модули по file:// не грузятся —
  поэтому генерация, а не ссылки).
- Makefile: цель `standalone` + чек в тестах `pytest`: standalone свеж
  относительно модулей (перегенерировать и сравнить хэш — дешёвый страж
  рассинхрона).

### Что сознательно НЕ меняем

Рендер, физика, состояние — переезд «как есть», без одновременной
переработки под «правильную архитектуру». Это чистый move-рефактор:
проверяемость = идентичные скриншоты до/после + `node --check` каждого
модуля + pytest (бэкенд не тронут) + smoke в headless-chromium.

### Порядок относительно фич

Рефактор **раньше** A–C: иначе каждая фича = двойные правки и мердж-
конфликты с самим переносом. После рефактора добавление фичи трогает
один-два модуля, и standalone пересобирается сам.

Гранулярность на старте (по выбору при постановке в работу): сразу
~10 модулей (выше) или промежуточно 3–4 (`assets+state+layout`,
`game.js` логика, `render.js`, `ui.js`). Полный вариант удобнее для
роста, границы всё равно уже обозначены комментариями-разделителями.

## Места в коде (`backend/app/static/game/`, после рефактора E)

- Игровой цикл: `frame()`/`update(dt)` — `main.js`, пауза здесь.
- Ввод: `act()` (`ui.js`), `jump()`, `trick()` (`player.js`),
  `keydown`/`pointerdown` (`ui.js`) — гейтинг.
- Тренер: `setCoach`, `coachStep`, `hud()` (cta/res) — `ui.js`, замена на гейты.
- Фичи трассы: `spawnFeatures`, `groundInfo`, `checkObstacles`,
  `drawRamp`, `drawFeatures`, `drawMarkers` — `features.js`.
- Полёт/трюки: `launch`, `land`, `stepTrick`, `physicsStep` — `player.js`;
  `award` — `ui.js`.
- Поза/рендер коровы: `poseMatrix`, `boardMatrix` (`player.js`), `drawCow`
  (`render.js`) — вращение на петле поверх этих.
- Константы: `CRUISE/MAXSPD/GRAV/OLLIE_V`, `OBS`, `TRICKS` — `constants.js`.
